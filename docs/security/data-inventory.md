# Data Inventory through Phase 1B-D2.2a

## Current boundary

Phase 1A is complete: exact released PDF/DOCX/text bytes can pass through the isolated
parser into encrypted immutable source-text storage, and an authenticated owner can
inspect and correct that text. Source-text content and extraction-job metadata are
included in the account privacy export; owner/document cascades erase them. Phase 1B-A
adds an in-memory provider-neutral model gateway, 1B-B1 adds strict evidence-linked
CV/JD output contracts, 1B-B2.1 adds encrypted immutable candidate-profile persistence
tied to one exact latest source-text revision, 1B-B2.2 adds durable fenced profiling
jobs, 1B-C1 adds a separately disabled policy-gated worker, and 1B-C2 adds authenticated
owner-only safe status/profile inspection and immutable evidence-revalidated correction.
Phase 1B-D1 adds the offline quality contract, D2.1 adds a concrete OpenAI Responses
adapter, and D2.2a adds a separately authorized private offline corpus/prediction/review
workflow. Provider execution remains disabled by default: no credential or real corpus is
bundled, no external call occurred during verification, and no public scheduling route or
continuous profiling supervisor exists. PostgreSQL stores
both source text and profile JSON as
AES-256-GCM ciphertext with keyed integrity metadata, never plaintext. There are no
passwords, email/name account profiles, interview answers, transcripts, evaluations,
embeddings, source-knowledge content, audio, or video.

## Controls and limitations

- UUID identifiers are opaque; application-created records use UUIDv7 and timestamps are UTC-aware.
- Preparation reads and writes require explicit scopes and exact owner matching. Cross-owner access is an opaque not-found response. Replacement/archive commands require a strong version precondition; create retries use an owner-scoped, hashed idempotency key.
- Candidate text is NFKC-normalized, trimmed, length-bounded, and rejects Unicode control/format/surrogate categories. Country is an uppercase two-letter ASCII code; role family, seniority, round, language, and status are controlled enums.
- Preparation audit, outbox, logs, and telemetry contain only allowlisted canonical metadata and opaque resource/version identifiers; company, role, office, and `other` text never enter those channels.
- Purpose, legal basis, consent, jurisdiction, retention, processor, and transfer metadata are policy/version inputs. No row means no processing.
- The initial jurisdiction registry is a routing catalogue, not evidence of legal compliance. Country enablement requires approved database policy records and the legal-review gate.
- Backup deletion is only complete when the outbox marker is durably copied to a separately protected control-plane ledger and restore replay is operational.
- Vendor locators are intentionally minimal and encrypted with authenticated field encryption. Real vendors still require a reviewed processor record and connector approval.
- Object-provider credentials are not application secrets in configuration; production uses workload identity and least-privilege access scoped to the approved bucket/KMS key.
- A document is not parser-readable until it has a clean, fresh-signature scan result and an exact active parser-release policy. Parser sandbox enforcement belongs to the separately gated Phase 1A-D unit.
- Upload/paste requires `preparation:write`, an owner-matched draft preparation, an 8-128 character idempotency key, and a supported raw-body media contract. The key is hashed; its request digest binds preparation/type/source/media/content digest. Both declared and streamed length are bounded, encoded bodies are rejected, and no filename is collected.
- Intake processing uses a five-minute lease/token and exact reserved UUIDv7 asset. Active retries return status, expired claims can recover, storage failure rotates only an asset already entering deletion, and downstream retries reuse the same released asset/version.
- Test and restore-rehearsal rows are synthetic.
- Release metadata and SBOMs contain no account identifier, token, secret, CV/JD content, interview data, or document bytes. Migration failure output intentionally excludes exception text.
- Telemetry contains only the allowlisted fields above. Trace/request IDs may correlate operational events but are never accepted as user identity or metric dimensions. Backend enrichment with client IP, geolocation, account data, or payload fields is forbidden.
- Encrypted source-text and candidate-profile tables, durable extraction/profiling-job
  tables, an isolated parser worker, a separately disabled profiling worker, and
  authenticated source-text/profile inspection/correction routes exist. There is no
  continuous worker supervisor, public profiling-schedule route, vector extension,
  embedding, full-text index, broker, Knowledge Base, RAG, or
  crawler.
- Source-text AES-GCM AAD binds owner, document/source/revision identities, origin/predecessor, exact parser provenance, counts, keyed digest, and key identity. The context-bound HMAC avoids a global plaintext equality oracle.
- Source-text storage reauthorizes purpose and rechecks active owner, draft/unexpired preparation, latest exact document version, released asset snapshots, delete-only retention, and exact active parser policy. LF-only and character/UTF-8 byte bounds reject unsafe Unicode control/format/surrogate input.
- Database triggers prevent source identity reassignment and all revision updates; a
  chain trigger enforces sequential immutable owner corrections. Extraction-job
  snapshots are protected from reassignment, and state constraints require a valid
  lease/result/error shape. Source-text/job access export and cascade erasure passed the
  Phase 1A-D4 gate.
- Profile persistence reopens and decrypts the exact latest source revision inside the
  write transaction, reauthorizes the processing rule, and independently repeats exact
  evidence-span validation. Exact retries are idempotent; changed output or release
  identity conflicts instead of overwriting an existing profile.
- Profile AES-GCM AAD and keyed digest bind exact source/document identity, immutable
  privacy/retention and model/prompt/schema provenance, bounded evidence counts, and key
  IDs. Profile aggregate identity and version chains are trigger-protected; lifecycle
  export decrypts through the narrow service and owner/document cascades erase rows.
- Owner profile reads return a completed profile only after exact job-result linkage and
  use `no-store`; active status omits worker/lease/processor internals. Corrections require
  strong `If-Match`, repeat purpose/privacy checks, revalidate exact retained-source
  evidence, and append encrypted `user_correction` history with content-free audit/outbox.
- Profiling jobs snapshot the exact owner/source, privacy/retention, model/prompt/schema,
  instruction/schema digest, and output-token limits before execution. Claims use
  `SKIP LOCKED` plus a five-minute UUID lease; stale tokens cannot mutate state. Attempts
  are capped at five with bounded backoff and explicit dead-letter state. Success is
  accepted only for an exact matching encrypted profile, and four database triggers
  protect immutable snapshots, transitions, and successful-result linkage.
- New profiling jobs also snapshot one approved processor activity whose processor key,
  privacy policy, purpose/category, and origin region are checked at schedule time. The
  worker repeats privacy authorization and registers the job UUID as an encrypted vendor
  deletion locator immediately before the external call. Revocation prevents the call.
- Code-owned CV/JD prompts treat source text as untrusted data and bind exact prompt and
  schema digests. The worker verifies those snapshots and configured model identity before
  sending content, then repeats exact-evidence validation before encrypted persistence.
- Model gateway settings reject partial or disabled coordinates. The runtime binds
  every success to exact model/prompt/schema identities and strict output validation,
  with bounded calls and payload-free representations. The OpenAI adapter is constructed
  only for explicit enabled OpenAI coordinates and a server secret; real profiling remains
  reachable only through C1 processor authorization, encrypted usage registration, and
  the separately enabled fenced worker path.
- CV/JD profile contracts require bounded exact source quotes for every derived claim.
  A separate verifier rejects wrong document types, out-of-range offsets, or substring
  mismatch before encrypted persistence. Schema-level PII minimization omits direct
  contact fields, but semantic PII filtering remains a future prompt/policy/quality
  control.
- The profile-quality evaluator is offline and size-bounded. Its input may contain the
  same sensitive content as candidate source/profile data, so non-synthetic corpora must
  stay outside version control under explicit rights, purpose, access, retention, and
  deletion controls. CLI output and invalid-input errors exclude content and file paths.
- Quality approval is stored separately from labeled evidence and binds the canonical
  evidence digest, exact model release, and policy version. The checked-in seed is
  synthetic and deliberately cannot meet release thresholds.
- The D2.2a generator is an explicit offline exception to the evaluator's no-provider
  rule. It requires a separately approved, active artifact bound to the exact private
  corpus digest, prompt digest, and OpenAI release plus an operator confirmation. It runs
  sequentially, writes only a new private file after completion, and does not create
  human adjudications or release approval.

Review this inventory at every schema change and before enabling any country, purpose, source, processor, replica, backup target, analytics sink, or operator access path.
